# HTML-строки: разбор, сериализация и координаты изменений

Дата проверки: 2026-09-15. Контекст: [HTML-строки: разбор, сериализация и координаты изменений](https://github.com/PaterSantyago/puncta/issues/27).
Исследование для core Puncta: синхронная обработка HTML-строки в ESM без браузерного DOM, с сохранением структуры и значений атрибутов, связным inline-текстом и позициями изменений в исходной строке.

## Вывод для следующего решения

**Основной кандидат — parse5 с собственным слоем соответствия текста исходнику.** Это рекомендация исследования, а не принятое архитектурное решение. Она предполагает, что эталоном структуры станет дерево, полученное стандартным HTML-разбором. Если требуется сохранять исходные теги даже при некорректной разметке, более подходящим направлением будет применение адресных замен к исходной строке; при этом происхождение текстовых сегментов всё равно нужно устанавливать корректным парсером.

Сам выбор парсера не решает четыре вопроса: какой контекст у фрагмента, что делать с некорректным HTML, где заканчивается связный текст и в какой узел помещать замену, пересекающую inline-границу. Готовой карты «каждый декодированный символ → исходный HTML» в рассмотренных высокоуровневых API нет.

Это обзор первичных источников и исходного кода. Производительность, размер browser bundle и исполнение в браузере не измерялись; продуктовый код и зависимости не менялись. Версии ниже — значения manifest в проверенных commit, а не утверждение о последнем опубликованном npm-релизе.

## Два кандидата

| Подход                                    | Что уже даёт                                                                                               | Основное ограничение для Puncta                                                                       |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| parse5: дерево + встроенная сериализация  | Document, contextual fragment, HTML tree construction, namespace/attributes, позиции узлов, ошибки разбора | Восстановленное дерево может отличаться от записи; позиции не являются картой декодирования           |
| htmlparser2 + domhandler + dom-serializer | События разбора или объектное дерево, индексы, декодирование entities, настраиваемая сериализация          | Семантика HTML не полностью совпадает с WHATWG; отдельный стандартный fragment-context API не заявлен |

### parse5

Проверенный [manifest parse5 8.0.1](https://github.com/inikulin/parse5/blob/30f320c07e4eef2711dfba5b2d578e05e28645f3/packages/parse5/package.json) задаёт ESM и зависимость `entities`. Публичные `parse`, `parseFragment`, `serialize`, `serializeOuter` работают с объектами tree adapter. Стандартный adapter создаёт обычные JS-объекты, а не использует `document.createElement`. Это основание считать направление пригодным для общего Node/browser core без DOM; browser-сборку выбранного релиза ещё нужно проверить. [API](https://github.com/inikulin/parse5/blob/30f320c07e4eef2711dfba5b2d578e05e28645f3/packages/parse5/lib/index.ts), [default adapter](https://github.com/inikulin/parse5/blob/30f320c07e4eef2711dfba5b2d578e05e28645f3/packages/parse5/lib/tree-adapters/default.ts).

`parseFragment(context, html, options)` разбирает строку в контексте заданного элемента, аналогично его `innerHTML`. Например, `<tr><td>…` требует контекста таблицы; документ и фрагмент не взаимозаменяемы. Puncta должен явно определить входной режим и способ задания контекста, а не определять его регулярным выражением. [Документация parseFragment](https://parse5.js.org/functions/parse5.parseFragment.html).

`sourceCodeLocationInfo` выключен по умолчанию. Включение добавляет locations; элементы, появившиеся при исправлении дерева, могут не иметь location. `onParseError` сообщает ошибки, а `scriptingEnabled` влияет на разбор `noscript`. Наличие callback не означает санитарную очистку или полную HTML-валидацию. [ParserOptions](https://parse5.js.org/interfaces/parse5.ParserOptions.html).

### htmlparser2 и dom-serializer

Сам автор htmlparser2 предупреждает о сокращениях алгоритма ради скорости и отсылает к parse5, если требуется точное соответствие HTML spec. API предлагает callbacks, `parseDocument`, настройку декодирования entities и индексов domhandler. `ontext` может сработать несколько раз для одного текстового узла. Поэтому callbacks удобны для потока сегментов, но их нельзя считать границами фраз. [README htmlparser2](https://github.com/fb55/htmlparser2/blob/18ad0d8fd4dcb61c7ad12b967a6839ebbf55e02f/README.md).

Проверенные [htmlparser2 12.0.0](https://github.com/fb55/htmlparser2/blob/18ad0d8fd4dcb61c7ad12b967a6839ebbf55e02f/package.json) и [dom-serializer 3.1.1](https://github.com/cheeriojs/dom-serializer/blob/a6a16a000d54a5705ade687156b5325ac44f0c03/package.json) имеют ESM entry points. Для синхронной строки не нужен отдельный Node `WritableStream`. В рассмотренном API парсера нет аналога параметра `fragmentContext` parse5: оборачивание строкой `<table>…</table>` не следует объявлять равноценной заменой стандартного fragment algorithm. [Entry API](https://github.com/fb55/htmlparser2/blob/18ad0d8fd4dcb61c7ad12b967a6839ebbf55e02f/src/index.ts).

У `Parser` есть `startIndex`/`endIndex` последнего события. В реализации текстовых событий конец включительный; при переводе в полуинтервал нужно прибавлять единицу. Декодирование entity тоже выдаёт текстовые события и двигает индексы. Многосимвольные entities требуют проверки отдельно: нельзя механически трактовать каждый callback как самостоятельный непустой диапазон исходника. [Parser.ts](https://github.com/fb55/htmlparser2/blob/18ad0d8fd4dcb61c7ad12b967a6839ebbf55e02f/src/Parser.ts).

## Что означает «сохранить HTML»

Здесь нужны разные контракты:

1. **Сохранить разобранное дерево:** менять только согласованные текстовые узлы, оставляя элементы, порядок дочерних узлов и значения атрибутов дерева.
2. **Сохранить исходную запись:** оставить все нетекстовые участки строки без изменений и применить адресные текстовые замены.
3. **Сохранить безопасную разметку:** отдельная политика допустимых элементов, атрибутов и URL. Это санитарная очистка, а не следствие первых двух контрактов.

HTML Standard определяет восстановление некорректного HTML: разбор может игнорировать повторные атрибуты, создавать элементы и переносить текст при обработке таблиц. Поэтому обещание сохранить все исходные атрибуты и исходную структуру для произвольного malformed HTML несовместимо с безусловным parse/serialize через стандартное дерево. [HTML parsing и примеры восстановления](https://html.spec.whatwg.org/multipage/parsing.html#an-introduction-to-error-handling-and-strange-cases-in-the-parser).

Сериализатор parse5 экранирует текст и атрибуты, записывает значения атрибутов в двойных кавычках, обрабатывает void elements и отдельно читает содержимое `template`. Raw-text элементы имеют особый путь. `serialize(element)` выводит содержимое элемента, а `serializeOuter(element)` — сам элемент целиком. Исходная форма entities, кавычки и написание doctype не сохраняются побайтно. [Реализация сериализатора](https://github.com/inikulin/parse5/blob/30f320c07e4eef2711dfba5b2d578e05e28645f3/packages/parse5/lib/serializer/index.ts).

dom-serializer позволяет выбрать Unicode или более широкое кодирование entities, формат пустых атрибутов и self-closing tags. Отключение encoding рассчитано на специальный round-trip с недекодированными сущностями; для изменённых декодированных текстов его нельзя автоматически применять. [Опции и реализация](https://github.com/cheeriojs/dom-serializer/blob/a6a16a000d54a5705ade687156b5325ac44f0c03/src/index.ts). Его собственный контракт описывает сериализатор как non-validating: он доверяет структурным полям дерева. Сохранённые обработчики событий и URL остаются исходными, если отдельная очистка их не удаляет. [Security policy](https://github.com/cheeriojs/dom-serializer/blob/a6a16a000d54a5705ade687156b5325ac44f0c03/SECURITY.md).

**Следствие для решения:** выбрать reject, возврат исходника с диагностикой или восстановление при ошибках должен пользователь. Даже при восстановлении типографические изменения и изменения сериализации лучше учитывать раздельно, иначе список «исправлений типографики» окажется заполнен изменениями кавычек атрибутов и вставленными тегами.

## Entities и координаты исходника

parse5 location задаёт начало и конец участка исходника; `endOffset` указывает позицию после последнего символа. Для публичного контракта Puncta естественный кандидат — полуинтервал `[start, end)` в UTF-16 code units исходной JS-строки. Это рекомендация, которую нужно явно утвердить; байты, Unicode code points и позиции после сериализации отличаются. [Location](https://parse5.js.org/interfaces/parse5.Token.Location.html).

Исходный код preprocessor считает позиции в JS-строке, учитывает surrogate pairs, преобразует CR в LF и пропускает LF после CR. Значит, простое `node.startOffset + decodedIndex` неверно даже без entities. [Preprocessor](https://github.com/inikulin/parse5/blob/30f320c07e4eef2711dfba5b2d578e05e28645f3/packages/parse5/lib/tokenizer/preprocessor.ts).

`entities` предоставляет `EntityDecoder`: callback получает code point и число поглощённых исходных символов; у entity с двумя code points callback вызывается дважды с одинаковым `consumed`. Есть режимы для текста, строгого декодирования и атрибутов. Это полезный строительный блок карты, но не HTML-парсер и не готовая карта всего документа. [EntityDecoder](https://github.com/fb55/entities/blob/0b16899dc04e08f7e8d9272c1365f36576f79113/src/decode.ts).

Предлагаемая модель собственного слоя, не реализация:

- Хранить последовательность сегментов: идентификатор текстового узла, локальный диапазон декодированного текста, один или несколько диапазонов исходника и вид преобразования (`literal`, `entity`, `newline`).
- Считать entity атомарным исходным участком. Если правило затронуло лишь часть её декодированного значения, замена исходной entity должна включить и оставшиеся символы; разрезать написание `&…;` нельзя.
- Сохранять provenance между последовательными правилами: последующее правило работает уже с изменённым текстом, а отчёт всё ещё должен ссылаться на оригинальный вход.
- Не выводить source mapping сравнением только конечных строк: одинаковые подстроки и повторные замены дают неоднозначное выравнивание.

Например, исходник `A&nbsp;<em>B</em>` содержит `A`, неразрывный пробел и `B` в двух текстовых узлах. Правило может видеть связный текст `A B`; изменение пробела относится к диапазону `&nbsp;`, а замена всей фразы — к нескольким текстовым диапазонам. Один общий source span включит `<em>`, поэтому он годится как диагностический охват, но не как инструкция заменить исходник целиком.

Для восстановленного дерева нельзя без проверки полагаться даже на непрерывность диапазона текстового узла: перемещение и объединение текста осложняет его происхождение. Нужны согласованные токены/сегменты либо явное ограничение поддерживаемых восстановлений. Экспортируемые низкоуровневые `Parser` и `Tokenizer` parse5 помечены `@internal`; опора на них повышает стоимость обновлений. [Маркировка API](https://github.com/inikulin/parse5/blob/30f320c07e4eef2711dfba5b2d578e05e28645f3/packages/parse5/lib/index.ts).

## Связный inline-текст и защищённые узлы

Предлагаемая схема: обход дерева создаёт текстовые серии; правила обрабатывают объединённый текст серии, а карта сегментов возвращает изменения соответствующим узлам. Inline-теги сохраняются. Компонент CSS layout в этом алгоритме отсутствует, поэтому определять границы по фактически вычисленному `display` в SSR нельзя; нужны согласованные семантические границы или пользовательская конфигурация.

Парсер различает raw text, RCDATA и обычный текст: `script` нельзя обрабатывать как `textarea`. HTML также отдельно описывает fragment context и scripting flag. Одно глобальное декодирование entities до разбора нарушит эти различия. [Состояния HTML tokenization](https://html.spec.whatwg.org/multipage/parsing.html#tokenization).

Набор защиты — продуктовый выбор. Для обсуждения: `script`/`style`/другие raw-text элементы; `pre`/`code`/`kbd`/`samp`; `textarea`/`title`; `template`; SVG/MathML; явно помеченные пользователем исключения. У пропущенного узла нужно решить ещё и роль границы: исключить его текст из серии недостаточно, иначе соседние фразы могут склеиться через невидимый для правил участок. `br`, изображения и комментарии также требуют явного поведения на границе.

На примере `<b>.</b>..` замена троеточия может затронуть два узла. Нужно договориться, где останется `…`, допустим ли пустой `<b>` и где считается insertion anchor на стыке. Парсер и сериализатор таких решений не принимают.

## Что остаётся решить и проверить

1. Фрагмент или документ по умолчанию; кто задаёт context element и namespace.
2. Семантика сохранения и реакция на ошибки разбора; отдельно — входит ли санитарная очистка в контракт.
3. Набор защищённых узлов, текстовые границы и поведение `template`/foreign content.
4. Политика распределения замен по inline-узлам и вставок на границах.
5. Диапазоны отчёта: UTF-16 исходника, список участков или один диагностический охват; отличаются ли типографические и сериализационные изменения.

Минимальный будущий проверочный корпус: contextual `tr`/`td`, полный документ, дубли атрибутов, незакрытые и misnested tags, текст около таблицы, `&amp;`/числовые/двухсимвольные/неполные entities, CRLF и emoji, RCDATA/raw text, `noscript` в обоих режимах, `template`, SVG, inline-разделённая замена, protected subtree и неизменность значений атрибутов. Одинаковые fixtures должны пройти в Node и browser build. Эти проверки здесь не выполнялись: исследование останавливается перед выбором политики и прототипом.
