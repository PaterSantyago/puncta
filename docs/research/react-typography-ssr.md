# React-разметка, streaming SSR и Server Components

Дата проверки: 15 сентября 2026 года. Исследование для [«React-разметка, streaming SSR и Server Components: технические границы типографа»](https://github.com/PaterSantyago/puncta/issues/26).

## Результат

Обработка переданной синхронной React-разметки до рендера совместима с обычным SSR и hydration. Общий текст через доступные inline-элементы технически можно собрать, преобразовать и распределить обратно. Это вывод из API элементов, а не готовая функция React. Скрытый результат пользовательских компонентов не доступен такому обходу. Настройки через React Context и определение того, какая область типографики преобразует конкретный текст, требуют разных механизмов. [Children](https://react.dev/reference/react/Children), [cloneElement](https://react.dev/reference/react/cloneElement), [useContext](https://react.dev/reference/react/useContext).

RSC — отдельный контракт. React 19.3 не предоставляет Server Components чтение Client Context. Варианты поддержки описаны ниже; ни один здесь не выбран. Исследование не утверждает, что scaffold уже обеспечивает перечисленные свойства.

## Что доступно обходу

| Вход                         | Факт React                                                                    | Следствие для будущего контракта                                                            |
| ---------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Строка, число, bigint        | Это отдельные листья в `ReactChildren`                                        | Определить участие чисел в текстовом контексте, не менять молча тип каждого числового child |
| `null`, `undefined`, boolean | При обходе считаются пустыми узлами                                           | Не превращать в видимый текст                                                               |
| Массивы                      | `Children` обходит содержимое; `toArray` уплощает структуру и вычисляет ключи | Нельзя терять ключи и менять структуру дерева без проверки сохранения состояния             |
| Host element, например `em`  | React element не раскрывается `Children.map` автоматически                    | Рекурсивный обход `props.children` должен быть явным и ограниченным согласованными типами   |
| `Fragment`                   | `Children` не заходит внутрь                                                  | Поддержать явно, сохраняя сам Fragment и его key/ref при преобразовании                     |
| Пользовательский компонент   | Полученный JSX не раскрывает его будущий render result                        | Оставить непрозрачной границей; подключать Puncta внутри компонента                         |

Источники таблицы: [Children](https://react.dev/reference/react/Children), [ReactChildren.js](https://github.com/react/react/blob/1d34f91dfde6bba84d08b683aaba164c7194dacb/packages/react/src/ReactChildren.js), [Fragment и сохранение состояния](https://react.dev/reference/react/Fragment).

`isValidElement` проверяет именно элемент: числа, массивы и portals также могут быть React nodes, но не проходят эту проверку. Поэтому условие «не element — значит строка» неверно. [isValidElement](https://react.dev/reference/react/isValidElement).

В полном ReactNode есть дополнительные случаи. Исходники React 19.3 обходят iterables и thenables; неразрешённый thenable может приостановить обход. Lazy-значение в структуре children может инициироваться самим `Children`; обычный элемент `<LazyComponent />` остаётся элементом. Значит, обещание синхронного безусловного обхода любого ReactNode было бы чрезмерным. Нужна явная политика для promises, iterables, lazy, portals и встроенных границ. Не следует копировать внутренние поля `_payload`/`_init`: здесь они изучены как ограничение, не как API Puncta. [ReactChildren.js](https://github.com/react/react/blob/1d34f91dfde6bba84d08b683aaba164c7194dacb/packages/react/src/ReactChildren.js).

Ручной вызов `Card(props)` для раскрытия дерева противоречит правилу React: компоненты вызывает React. Даже видимые `children` пользовательского компонента не гарантируют будущий порядок и присутствие текста: компонент может их отфильтровать или повторить. `memo`, `forwardRef` и пользовательские обёртки не дают разрешения раскрывать их реализацию. [React calls Components and Hooks](https://react.dev/reference/rules/react-calls-components-and-hooks).

## Текст через inline-разметку

**Архитектурный вывод:** для `"Hello <em>world</em>"` и `24 <strong>kg</strong>` возможен сбор последовательности текстовых листьев с адресами в исходном дереве; core получает текст и границы, возвращает изменения; React-адаптер заменяет только соответствующие children. `cloneElement` позволяет заменить children, сохранив остальные props, key и ref, если их не переопределять. [cloneElement](https://react.dev/reference/react/cloneElement).

Одной итоговой строки недостаточно для надёжного восстановления: замена `...` одним знаком изменяет длину, а знак или удаляемый пробел могут находиться на границе двух листьев. Нужна политика привязки вставок и удалений к листьям, сохраняющая разметку. Это также связано с позициями изменений подробного результата. Возможные представления — список правок исходных диапазонов либо сегменты с привязкой к источнику; выбор остаётся за спецификацией core.

Граница блока, `br`, защищённый фрагмент, неизвестный компонент и вложенная область с другой локалью требуют отдельных решений. Не следует считать их просто пустой строкой: исчезнувшая граница может ошибочно склеить соседние слова. Определение inline по доступному имени тега будет семантической политикой библиотеки, а не вычислением фактического CSS layout; сервер не располагает браузерной геометрией. Приведённые примеры реализуемы без обещания обработки через произвольные границы.

`dangerouslySetInnerHTML` задаёт HTML отдельным prop, а не деревом React children. Поэтому автоматическое преобразование этого prop не следует из согласованной поддержки React-разметки. Вариант — отдельный явный вызов режима HTML-строк; нужно согласовать интеграцию и защищённость. Аналогично `title`, `alt`, `value`, `placeholder` требуют отдельного согласованного охвата. [Common DOM components](https://react.dev/reference/react-dom/components/common).

## Вложенные области: настройки и владение текстом

`useContext` читает ближайший Provider выше текущего компонента. Provider, возвращённый тем же компонентом, не меняет значение уже выполненного `useContext`. React передаёт значение целиком и не выполняет частичное слияние настроек. Слияние наследованных настроек с явно переданными переопределениями — ответственность Puncta. Несколько копий модуля контекста могут разорвать наследование: объект контекста у Provider и consumer должен совпадать. [useContext](https://react.dev/reference/react/useContext).

**Ключевое следствие:** parent не должен сначала необратимо типографировать текст вложенного Puncta по своей локали, а потом передавать получившийся текст дочернему Puncta. Дочерний Provider не восстановит исходные кавычки, пробелы или выключенные правила. Идемпотентность при одинаковых настройках не исправляет применение разных настроек.

Два варианта для обсуждения:

1. **Каждая область владеет своим исходным текстом.** Родитель останавливается на вложенном Puncta; тот читает унаследованные настройки и обрабатывает свой исходный input. Это естественно исключает предварительную обработку дочернего текста. Цена: отдельное решение, разрывает ли вложенный Puncta общий текстовый контекст даже при одинаковых настройках.
2. **Единый проход по известным областям.** Родитель распознаёт собственные вложенные области, вычисляет эффективные настройки до преобразования и координирует правки. Цена: явное представление областей и владения исходниками, отсутствие второго преобразования при последующем рендере дочернего компонента, реакция на изменение локальных props/Provider. Через неизвестные компоненты такой проход всё равно не проходит.

Оба варианта — выводы для выбора, не решения API. Особенно нельзя переносить вычисленные родителем настройки через произвольный компонент, внутри которого появится неизвестный ему Provider: фактический контекст определится только при рендере.

Локальные вычисления должны зависеть от исходных props/context. Общий изменяемый «текущий язык», глобальный буфер кавычек или глобальная отметка «уже обработано» делают результат зависимым от порядка рендера и соседних запросов. React допускает повторный и прерываемый render и запрещает изменять нелокальные данные во время него. Подробную диагностику тоже нельзя публиковать побочным эффектом при каждом render: повторный render не равен повторному действию пользователя. [Purity rules](https://react.dev/reference/rules/components-and-hooks-must-be-pure).

## SSR, hydration и streaming

Hydration требует одинакового начального содержимого на сервере и клиенте; расхождения нужно исправлять. Для Puncta это означает одинаковые исходники, эффективные настройки, локальные данные правил и детерминированное преобразование в обоих окружениях. Пропуски, мягкие переносы и неразрывные пробелы входят в сравниваемый текст. `suppressHydrationWarning` не является доказательством корректности. [hydrateRoot](https://react.dev/reference/react-dom/client/hydrateRoot).

Обработка только в Effect не даёт уже оттипографированный HTML на сервере: Effects на сервере не исполняются. Следовательно, согласованный SSR предполагает преобразование в render или ранее, до передачи данных компоненту. [useEffect](https://react.dev/reference/react/useEffect).

`renderToString` не поддерживает streaming и не ожидает приостановившееся дерево. Текущий пример подтверждает лишь техническую интеграцию пакетов. [renderToString](https://react.dev/reference/react-dom/server/renderToString).

`renderToPipeableStream` передаёт shell, затем готовые участки Suspense; fallback и итоговое содержимое доступны в разные моменты. **Вывод:** синхронный локальный проход Puncta совместим с этим устройством, но не может получить ещё не отрендеренный текст соседнего компонента. Общий контекст через асинхронную границу потребует ожидания/буферизации и изменит момент выдачи HTML. Уже переданный текст нельзя исправить обычным локальным render другой области. Не следует предварительным раскрытием обещаний в родительском обходе случайно переносить suspension выше предназначенного ему Suspense. [renderToPipeableStream](https://react.dev/reference/react-dom/server/renderToPipeableStream), [ReactChildren.js](https://github.com/react/react/blob/1d34f91dfde6bba84d08b683aaba164c7194dacb/packages/react/src/ReactChildren.js).

Варианты политики Suspense: непрозрачная граница с явным Puncta внутри content/fallback либо отдельная обработка известных статических ветвей без склеивания их друг с другом. Поддержка Web Streams проверяется отдельно через `renderToReadableStream`, если этот runtime входит в первую версию. [renderToReadableStream](https://react.dev/reference/react-dom/server/renderToReadableStream).

## Server Components: факты и варианты

RSC выполняются в окружении, отдельном от обычного SSR. Server Component может отрендерить Provider, импортированный из Client module; его значение читают Client Components. Это не делает значение доступным Server Components. [Server Components](https://react.dev/reference/rsc/server-components).

В React 19.3 server entry не экспортирует `createContext`/`useContext`; Flight dispatcher отвергает чтение Client Context, в том числе через `use`. Это конкретное ограничение реализации выбранной версии. [ReactServer.js](https://github.com/react/react/blob/1d34f91dfde6bba84d08b683aaba164c7194dacb/packages/react/src/ReactServer.js), [ReactFlightHooks.js](https://github.com/react/react/blob/1d34f91dfde6bba84d08b683aaba164c7194dacb/packages/react-server/src/ReactFlightHooks.js).

| Вариант                                    | Возможности                                                                    | Цена и предел                                                                                                           |
| ------------------------------------------ | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| Client entry для Puncta/Provider           | Context и вложенные настройки в Client tree; RSC может импортировать компонент | Код обработки попадает в клиентское поддерево; сборка должна сохранить директиву; это не Server-native Provider         |
| Чистая функция core в RSC                  | Оттипографировать строку на сервере с явными настройками                       | Наследование React Provider на сервере отсутствует; настройки нужно передать явно или замкнуть в настроенном экземпляре |
| Отдельный Server-compatible React entry    | Обработка доступного JSX без client-only context                               | Дополнительный экспорт и отдельный контракт наследования; неизвестные компоненты по-прежнему непрозрачны                |
| Пока не обещать специальную RSC-интеграцию | Сосредоточить первую версию на согласованных SSR/hydration/streaming           | Отдельно документировать путь использования чистой функции; RSC-компоненты не считать проверенными                      |

Основания вариантов: [`use client`](https://react.dev/reference/rsc/use-client), [Server Components](https://react.dev/reference/rsc/server-components), [ReactServer.js](https://github.com/react/react/blob/1d34f91dfde6bba84d08b683aaba164c7194dacb/packages/react/src/ReactServer.js). Это варианты для владельца, не рекомендация выбрать один автоматически.

Директива `use client` задаёт границу модулей, а не запрещает SSR Client Components. Передаваемые из Server в Client props должны быть сериализуемы по правилам React. Обычный объект локали с функциями правил или настроенный экземпляр класса может не пройти эту границу; возможные решения — сериализуемый идентификатор/настройки или импорт локали внутри Client module. JSX допустим как prop, но это не обещание готового синхронного дерева для обхода при любом streaming-сценарии. [`use client`](https://react.dev/reference/rsc/use-client).

Не требуется писать собственный Flight decoder или интегрироваться с внутренностями React. API реализации RSC-bundler/framework не следуют semver между minor React 19; такую интеграцию нельзя выводить из одного peer-range `^19.3.0`. [Server Components](https://react.dev/reference/rsc/server-components).

## Что проверить после выбора контракта

Это будущие сценарии приёмки, а не выполненные тесты:

- Строки, числовые листья, пустые узлы, массивы, keyed Fragment; состояние дочернего компонента, ref и обработчики событий после смены текста.
- Кавычки и неразрывная связь через `em`/`strong`; правка, пересекающая два листа; многоточие и алгоритмический мягкий перенос без повреждения привязки правок.
- Блоки, `br`, защищённые фрагменты, custom elements, `dangerouslySetInnerHTML`: соблюдение выбранной политики границ.
- Вложенная локаль и отключённое правило получают исходный текст; повторный render и переключение Provider не оставляют результаты старых настроек.
- Неизвестный `Card` скрывает текст от внешнего обхода, а Puncta внутри него наследует фактический ближайший Provider.
- Два одновременных SSR-запроса с разными дефолтами и приостановкой одного не влияют друг на друга.
- `renderToString` → настоящая браузерная hydration: одинаковый текст и отсутствие неожиданных hydration errors; дальнейшее изменение настроек работает.
- Streaming с задержанным content, fallback и соседней областью: shell приходит своевременно, после раскрытия текст верен; retry/abort не оставляет общего состояния. Проверить promises в children против выбранного контракта.
- Для выбранного RSC-варианта: реальный framework fixture, серверный импорт, сериализация props, Client Provider, async Server child и собранные экспорты. Проверка только `node --conditions=react-server` выявляет ошибочные импорты, но не заменяет такой fixture.

## Оставшиеся решения

Нужно выбрать модель владения исходным текстом, границы текстового контекста и async children, правила привязки правок к листьям, охват React props, минимальный streaming runtime и уровень RSC-поддержки. Исследование подтверждает ограничения и допустимые направления; точный публичный API, результаты языковых правил и гарантии производительности ещё не определены.
